# 第二轮：通信与 HC 后处理融合

本轮目标是普通生成与长上下文。权重、路由、草稿模型、验收规则、采样和数学精度均保持不变；按相同权重分别比较，不把 E320 与 A0 的差异算作引擎收益。

## 新实现

`prepare_transport.py` 从固定 TensorFold 源码生成独立扩展。上游的内存注册、双网口代理、RDMA 写入、完成通知和异常中止机制保留；新增部分是有界分段、双段流水线，以及直接消费接收环的 HC 后处理 CUDA 内核。

普通路径先生成 rank 顺序的完整 gathered 张量，再执行 HC 后处理。新路径在每个分段抵达后读取本地和远端部分和，按 rank 0、rank 1 的顺序进行 FP32 加法，保留原有 BF16 舍入边界，再按相同 FMA 链更新四路残差。它省掉 gathered 中间张量的写入和读取，不压缩网络数值，不改变模型精度。

每段的序号写进单独的 GPU ticket。两个 segment 可以先入队，再依次收集；至少四个 ring slot 保证前一批完成后才可能复用旧批的接收槽。每段有同样的双网口发送、大小通知、接收完成与中止检查。注册环仍为约 51 MiB，而非扩大到覆盖整个 prompt。CUDA Graph 捕获的序号在重放时推进。

解码中，`postmix.py` 让已写好的残差立即进入 collapse/RMSNorm，将下一子层需要的 HC 混合与 Sinkhorn 留在侧流上。它复用上游数值内核、归约树和既有 join，不把这些内核宣称为本项目的新算法。

启动时两端通过 store 校验功能开关、Python/CUDA 源码、四个引擎覆盖文件和成本表。在加载权重与捕获通信图之前拒绝不一致配置。

## 不变量

- 恰好两个 rank，FP32 部分和与 BF16 残差，D 可被 4 整除，最大 256 MiB 部分和。
- 不改变 rank 加法顺序、BF16 边界、HC FMA 顺序、token 验证与采样。
- 不同请求不会共享草稿状态；环序号跨 kernel 与 graph replay 单调推进。
- 无可用 RDMA 时保留原通信路径；运行期间保留上游 watchdog/abort 机制。本轮完成了错开时序与环覆盖验证，尚未对这条新增路径做实机 RDMA 断链注入，不能把它当作完整的故障恢复验证。
- `SPARK1017_RDMA_POST=0|prefill|decode|all` 独立控制场景，默认 0。其他实验模块默认关闭。

## 验证方法

1. 双机通信字节、HC 输出在 eager 与 CUDA Graph 中逐位比较。
2. 100 个改变载荷并故意错开两端执行时间的事务检查旧数据覆盖。
3. 解码侧流比较残差、归一化输出、HC 系数与有效中间状态，并重放图。
4. 固定公共客户端、相同 prompt token IDs、上下文池、并发、采样和输出预算，记录完整响应。
5. 独立 SciCode 开发回归与 CanItEdit 冻结子集；代码只在隔离容器执行。

微基准收益与端到端收益分别报告。采样次数不等的试验筛选不参与最终公平排名。较早的 serial HC 版本保留为失败/中间记录，不能替代最终版。

预填充也测试了类似的系数侧流调度。虽然所有有效中间状态逐位一致，但实际长输入收益回退，因此 `SPARK1017_PREFILL_SIDE` 保持关闭；解码中用于保持原有并行顺序的 `postmix.py` 仍保留。

## 其他已试路线

4090 增量同步 DSpark 草稿、专家 occupancy 工作列表、持久化任务队列、直接 fragment 链、控制消息合并均有独立实现和验证。它们对本轮完整负载没有稳定、足够的收益，保留为默认关闭的实验。4090 在正式速度对照中负责测量与隔离评分；远程草稿试验单列，因为它额外占用 GPU。
